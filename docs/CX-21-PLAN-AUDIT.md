## B. SQLite decision

This is an **Expo managed/CNG (prebuild) project, not a checked-in bare app**: it pins Expo 57/RN 0.86 and its Android script generates `android/` with `expo prebuild`; the checkout has no `apps/mobile/android/`. It already carries one local Expo Android module, so native dependencies are allowed but require prebuild and a new native binary (`apps/mobile/package.json:11-30`, `apps/mobile/package.json:42`, `apps/mobile/modules/photeo-scan-service/expo-module.config.json:1-9`). The New Architecture is active: the ML layer explicitly identifies these as New-Architecture paths and records RN 0.86 as forced-New-Architecture (`apps/mobile/src/ml/README.md:3-15`, `apps/mobile/src/ml/README.md:38-43`).

No SQLite driver is installed (`apps/mobile/package.json:5-33`). Repository-side decision:

| Driver | This build | BLOB path | Decision |
|---|---|---|---|
| `expo-sqlite` | Directly compatible with Expo CNG and least native integration surface; still requires adding the native package and rebuilding. | Its native API exposes BLOB values as `Uint8Array` (backed by `ArrayBuffer`), so application code need not base64-encode. Zero-copy across the JS/native boundary is **not established by this repo** and needs a microbenchmark. | **Recommend**, behind a small storage interface plus a 17.7k×512 BLOB read/heap benchmark before migration. |
| `@op-engineering/op-sqlite` | Native/JSI is possible in a prebuild app, but no dependency, config plugin, compatibility proof, or generated Android project is present. | ArrayBuffer support is an upstream claim, not verifiable from this checkout. | **Unverified; do not select on plan text alone.** |
| `react-native-nitro-sqlite` | Nitro runtime happens to be present because fast-tflite uses it, but the SQLite driver is not; RN 0.86 compatibility is not demonstrated here. | ArrayBuffer/zero-copy behavior is not verifiable from this checkout. | **Unverified.** Existing `react-native-nitro-modules` is not evidence that this database driver works (`apps/mobile/package.json:28-30`). |

Adding `expo-sqlite` is not a bare-workflow conversion, but M1 is still **XL**, not a package-add: it must replace two crash-sensitive persistence paths, preserve IDs/clusters, import incrementally, dual-read, and avoid re-materializing 9M embedding scalars as JS arrays. Today persistence explicitly guards against wiping 17,699 faces, writes the whole JSONL through a temporary file, and dequantizes each int8/base64 vector to `number[]` (`apps/mobile/src/faces/face-index.ts:1262-1287`, `apps/mobile/src/faces/face-index.ts:1328-1361`, `apps/mobile/src/faces/face-index.ts:1392-1415`, `apps/mobile/src/faces/face-index.ts:814-831`).
